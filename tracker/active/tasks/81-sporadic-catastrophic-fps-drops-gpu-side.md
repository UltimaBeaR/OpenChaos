# 81 — Sporadic catastrophic FPS drops (GPU-side)

- Status: ❄️ deferred
- Area: platform
- Tags: analysis, bug, intermittent
- Created: 2026-10-27
- Related: migrated from the old list `archive/known_issues_and_bugs/known_issues_and_bugs.md`

## Description
**Reproduces randomly** on various missions. After loading a level, the FPS is suddenly low across the whole level (street ~17-20 fps instead of 200+, indoors ~60-90 fps instead of ~300). There are no heavy processes in the system. **What does NOT help in most cases:** alt-tab. **What helps:** **resizing the window** (resize → re-maximize) — recreates/reconfigures the GL surface and kicks the GPU back into high frequencies. Less often — restarting the game process helps. **Nature:** in several cases caught via the perf panel in glFinish mode — **ONLY the GPU** slows down (every GPU operation uniformly gets more expensive), the CPU is negligible. The signature of a **GPU frequency drop** boost→idle, not of a specific piece of work getting more expensive. **Hypothesis:** the GPU goes into a low power state and underclocks under a light/choppy load; resizing forces the driver to reconfigure the surface and kicks the GPU back. The target hardware (Steam Deck / integrated graphics) is prone to aggressive power-gating. **Suspected triggers:** minimizing the window; long background audio from other applications (YouTube). ~~**Solution for 1.0 — workaround:** automatically perform the same action as a manual resize — on every alt-tab (regaining focus) and after a mission load.~~ **REJECTED — see the 2026-06-08 research below.** **Deep investigation of the root cause (driver / power-state / compositor) — post-1.0.** **Observation (new):** caught again in **windowed mode** — this time **neither resizing the window nor alt-tab helped**, only **restarting the game** helped. So "cured by resize" is not universal: there's a state from which reconfiguring the GL surface (resize/alt-tab) **doesn't kick** the GPU back into boost, and only a full restart of the process saves it. This weakens the hypothesis "the driver underclocks under our load and a resize wakes it" — it seems sometimes the GPU/driver gets stuck deeper (or this is a different sub-case entirely). **Important for the 1.0 workaround:** auto-resize on alt-tab may NOT remove the symptom in some cases → we need either a stronger "wake-up" (context recreation?), or to accept that some cases are only cured by a restart. **Research 2026-06-08 (decision: for 1.0 we do NOT make a workaround, accept it as is):** (1) **A clean cross-vendor in-app way to force high GPU frequencies doesn't exist.** All the real levers are driver/OS/user-level: NVIDIA "Prefer Maximum Performance" (only via a driver profile = NvAPI → vendor-lock, rejected by the user earlier), AMD/Steam Deck — a manual GPU frequency lock in Dev Mode (a slider in the Quick Access Menu, user-level), registry / MSI Afterburner / ClockBlocker (user-level). (2) **"Mark the process as requiring a high GPU" — there's no such Windows API.** Windows per-app GPU preference (`GpuPreference=2` in `HKCU\…\DirectX\UserGpuPreferences` / `DXGI_GPU_PREFERENCE_HIGH_PERFORMANCE`) and the export symbols `NvOptimusEnablement`/`AmdPowerXpressRequestHighPerformance` control **only GPU selection** (discrete vs integrated on hybrid laptops), **not frequencies**. The symbols are **already exported** for us ([`main.cpp`](../../../new_game/src/main.cpp) ~L42) — they don't cure our problem, on single-GPU systems (Steam Deck) they're a no-op entirely. `SetStablePowerState` (D3D12) locks at the **base** frequency (disables boost) — makes it worse. (3) **The only in-app lever** is to artificially load the GPU (filler workload) so the governor keeps the frequencies up. **Rejected:** it directly contradicts the target (Steam Deck / integrated — extra heat, battery drain, fan), plus it's a steady-state crutch against an **intermittent** stuck state (the fake load would have to run constantly). (4) Auto-resize/alt-tab are themselves unreliable (some cases are only cured by a restart, see above). **Conclusion:** a driver-platform problem with no clean app-side fix → for 1.0 we accept it as is; optionally document the standard fixes for the user (NVIDIA "Prefer Max Performance", the Deck's manual clock). **Possible post-1.0 path** (if revisiting): a runtime stuck-state detector (the perf panel already catches it via glFinish — GPU operations uniformly get more expensive with negligible CPU) + a pointwise wake-up **only** when actually stuck (not on every alt-tab), with escalation; but with no guarantees it'll pull it out of a deep stuck state.
